# Last.fm interaction audit

Audited 2026-09-05 against `bdfc933`, using executable source and controlled tests. Repository documentation was not used as evidence of behavior. This is an audit; production behavior is unchanged.

Follow-up: [type-ahead performance audit](typeahead-performance-audit.md) measures autocomplete, filtering, search admission, and keyboard prefix navigation across both windows.

The frustration has a concrete cause: ordinary importer edits use a **save, then refresh, then re-enable** interaction model. The backend additionally performs full-session cloning and durable writes before acknowledging tiny edits. A background apply queue already exists, but it shares locks with foreground reads and edits, so putting work in that queue does not isolate the UI from it.

I would adopt your proposed contract for review metadata: acknowledge accepted intent in memory, keep unrelated controls usable, and persist asynchronously. The current implementation does not meet a 5 ms acknowledgement budget. A queue alone will not fix it if its admission path still clones the session, waits for Spotify, or saves to disk.

## Evidence and limits

Three opt-in tests mount the real React importer with deferred IPC promises. They demonstrate actual control state and calls, not browser frame times:

1. Clicking Include immediately changes the checkbox, but disables queue navigation until **both** `lastfm_import_options` and the subsequent queue refresh finish. Pressing Space on the source row submits another options request while those mouse controls are disabled.
2. Exclusion updates before acknowledgement and keeps Undo enabled. Queue navigation remains disabled while the request is pending.
3. A collection preview's invalidation event invokes `lastfm_import_state`, `lastfm_import_queue`, and `lastfm_import_page`, even though the preview command itself returns the updated page.

An opt-in Rust benchmark calls the real service and filesystem stores in an optimized release build. Each fixture has three source rows per release, one album candidate per row, three tracks per candidate, and no queued jobs or network. Medians of three successive measurements on this Mac:

| Session | Compact JSON | Full snapshot clone | Build one page | Queue page, up to 1,000 batches | Change one genre and save | Repeat identical options |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 100 batches / 300 rows | 0.26 MB | 0.23 ms | 0.14 ms | 0.27 ms | 5.88 ms | 0.58 ms |
| 1,000 batches / 3,000 rows | 2.61 MB | 2.57 ms | 1.39 ms | 3.17 ms | 16.64 ms | 5.81 ms |
| 5,000 batches / 15,000 rows | 13.24 MB | 12.94 ms | 6.14 ms | 4.10 ms | 63.57 ms | 28.72 ms |

These are **service timings**, excluding Tauri serialization, frontend work, use-case account checks, lock contention, and refresh fanout. They are not measurements of your live import or predictions of its precise latency. Candidate-rich sessions can be much larger. The no-op still pays for clones and equality checks but skips disk persistence. The changed-options timing includes serialization and the atomic file save, not just physical disk time.

The existing `aborted_import_session_save_finishes_disk_and_memory_publication` test also exercises a held filesystem save: the in-memory state remains old until the write is released. This confirms the persistence-before-publication contract in executable code.

No live account was mutated. No browser profiler trace, real IPC p95, or measured before/after improvement is claimed. The user's estimated 40–50% frequency was not measured; the audit confirms widespread blocking pathways, not that percentage.

## Shared costs behind the action matrix

The matrix uses the following names to avoid repeating the same long chain in every row.

**Account gate.** `ensure_import_readable` clones the session; for Spotify-owned review it validates identity through `current_spotify_binding_is_current` and `current_account_binding`. Those routes acquire the Spotify membership mutex and take further snapshots. Exact cached membership avoids `/me`; incomplete membership can require an awaited identity request. Most mutations acquire the same mutex and hold it through their save. See [read validation](../apps/desktop/src-tauri/src/lastfm_import.rs), functions `ensure_import_readable` and `current_spotify_binding_is_current`, and [collection.rs](../apps/desktop/src-tauri/src/lastfm_import/collection.rs), `current_account_binding` and its callers.

**Session save.** `Service::mutate_session` acquires the persistence gate, recovers any pending transaction, deep-clones the old session, clones it again for mutation, compares the full result, and clones the changed session for the blocking save task. Only after that task succeeds does it replace the in-memory session and return. The store serializes compact JSON and calls `atomic_write`, which writes, `sync_all`s, and replaces the file. File I/O is correctly off the async runtime, but the caller still waits. See [service.rs](../apps/desktop/src-tauri/src/lastfm_import/service.rs), `mutate_session`, and [store.rs](../apps/desktop/src-tauri/src/lastfm_import/store.rs), `ImportSessionStore::save`; [persistence.rs](../apps/desktop/src-tauri/src/persistence.rs), `atomic_write_inner`.

**Review transaction.** Exclude/undo, skip/restore, ignore, and count-mode changes go through `mutate_review_state`. It clones session and mappings, writes a recovery transaction containing both, writes the session, writes mappings, clears the transaction, then publishes memory. This is stronger durability than a simple edit acknowledgement. Even a change that leaves mappings unchanged uses the transaction path if the session changed. Ignore actions can additionally reconcile the incremental backlog, clone the library, write a reconciliation journal, and rebuild review data. See `mutate_review_state`, `review_action`, `set_count_mode`, and `sweep_backlog_with_mappings` in [service.rs](../apps/desktop/src-tauri/src/lastfm_import/service.rs).

**Full refresh.** Frontend `refresh()` concurrently requests state and **all queue pages**, then requests the selected page. Queue pages are fetched sequentially in chunks of 1,000; a changed total can trigger one full retry. Every queue command passes read validation again. Each service queue page scans session rows and reconstructs batch metadata. `refreshQueueOnly()` still reloads state and the entire queue, but skips the selected page. See [LastFmImporter.tsx](../apps/desktop/src/LastFmImporter.tsx), `loadImportQueue`, `refresh`, and `refreshQueueOnly`.

**Page load.** `Service::page` is a computed projection, not an indexed record read: it holds the session mutex, obtains sync state, filters/clones batch data, scans source rows, computes required matches/count information, clones candidate payloads for rows, and constructs state/collection views. The public page command adds account validation and lazy matching. Cached collection pages still rerank, enter the session mutation path, and rebuild the page; an unchanged result skips the disk write, but not all cloning/comparison/computation. See [service.rs](../apps/desktop/src-tauri/src/lastfm_import/service.rs), `page`, and [coordinator.rs](../apps/desktop/src-tauri/src/lastfm_import/coordinator.rs), `lazy_match_page`.

**Busy scope.** The review pane has a `busy` flag and tells the root about page mutations. This disables queue navigation, sorting, bulk queue selection, and many review controls. It is not a blocked JavaScript event loop: typing in the queue filter, some focus movement, help, and certain dialog controls can still work. Root-only busy operations do not consistently disable the review pane. This uneven scope matters for correctness as well as perceived speed.

### Keyboard and background-event cross-check

Native buttons, checkboxes, radio buttons, selects, labels, and forms use their native activation paths. The importer reserves shortcuts only on its navigation targets, preserving typing and ordinary modal controls. Mapping ↑/↓ and Tab move focus locally; Enter enters native controls; Escape leaves control mode or closes a dialog; `?` opens the local legend. Queue ↑/↓ differs from Enter as described above. There is no separate importer file-drop, paste-to-import, or row-reorder backend pathway; paste is input text, and drag handlers here move/resize presentation.

The busy mismatch is real: mouse controls use `disabled`, but mapping Space/S/A and E do not first check `busy`. X does go through `rejectRows`, which explicitly permits only its own pending rejection stream. Concurrent actions can make the first request's `finally` clear a shared boolean while a second is still active. This is a code-verified race risk; the mounted Space test proves duplicate admission, not a specific lost edit. Merely removing `disabled` everywhere would expand this problem.

`lastfm-import-changed` normally triggers a full refresh. Parent-owned review mutations suppress their own invalidation and explicitly reconcile; genre saves, search-term changes, and dialog-owned collection operations do not consistently use that suppression. Successful apply events refresh the selected batch only when appropriate; failures refresh queue/state and show structured errors. Generation checks prevent many stale responses from replacing a newer page, but discarded requests still consume backend work. The main app separately reloads importer state for its status bar on invalidation, adding another reader of the same account gate.

| Priority | Finding | Smallest useful direction | Proof required after a fix |

The first four fixes address the everyday “click, then wait for permission to click again” experience. They do not require a new broker, database, generalized task framework, or queue per field. An in-process service-owned patch queue/coalescing writer is enough to start. Existing apply jobs can remain the mechanism for explicit content actions.

The durability tradeoff should be explicit: accepting draft metadata in memory can lose the latest unflushed edits on a crash. That matches the requested preference. Atomic file replacement can remain in the background. Keep account boundaries, input validation, and duplicate-apply/play-count protection: those are separate concerns from whether a genre checkbox waits for `fsync`. A 5 ms timer cannot make disk I/O deterministic; do not put a full serialization/save attempt in the acknowledgement path and assume it will finish inside that timer.

Proposed acceptance target: local visual feedback without waiting for IPC; in-memory admission p95 ≤5 ms with no disk/network dependency; independent navigation usable while searches/applies/saves are held; eventual persistence failures surfaced without rolling back newer accepted edits. Measure event-to-paint separately from command receipt-to-ack, and test normal releases plus large custom collections. Those targets are recommendations, not achieved performance claims.
